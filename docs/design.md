# Skill 设计文档：周报/日报自动生成

## 一、概述

### 1.1 目标

为不同角色的团队成员提供自动化的周报/日报生成能力：

- **项目/产品人员**：基于项目管理工具（JIRA/TAPD/禅道等）的任务数据生成报告
- **技术人员/开发人员**：融合项目管理工具任务 + Git Commit 代码提交信息生成完整报告

### 1.2 角色识别与报告适配

本 Skill 支持**自动识别用户角色**，根据角色生成不同格式的报告：

| 角色类型 | 识别方式 | 报告特点 |
|---|---|---|
| **产品/项目人员** | 未提供 commits.json 或 Commit 与 Issue 无关联 | 侧重任务进度、需求管理、项目推进 |
| **技术/开发人员** | 提供 commits.json 或 Commit 与 Issue 有关联， 在任务基础上增加代码功能描述、技术方案，若与 Issue 无关联，则直接当一个开发项描述，描述功能 |

**角色声明方式**：

用户可以在生成周报时主动声明角色：

```
请根据我上传的 issues.csv 生成周报。
姓名：蛋仔
角色：产品经理
```

或

```
请根据我上传的 issues.csv 和 commits.json 生成周报。
姓名：蛋仔
角色：开发人员
```

**Assignee 的多重含义**：

| 角色 | Assignee = 本人的含义 | 报告展示 |
|---|---|---|
| 开发人员 | 负责代码开发 | 「开发项」+ 代码详情 |
| 产品经理 | 负责需求管理 | 「负责任务」+ 进度状态 |
| 测试人员 | 负责测试执行 | 「测试任务」+ 测试结果 |
| 项目经理 | 负责项目推进 | 「负责任务」+ 整体进度 |

### 1.3 智能筛选逻辑

本 Skill 采用**双轨筛选机制**，确保周报内容完整：

| 筛选条件 | 含义 | 报告分类 |
|---|---|---|
| **Assignee 是本人** | 自己是该任务的负责人/开发者 | **开发项** |
| **Comment 中有本人** | 本人在该任务下回复或跟进过 | **跟进内容** |
| **Watcher 是本人** | 本人关注该任务的进展 | **跟进内容** |
| **Reporter 是本人** | 本人创建的任务 | **跟进内容** |

**为什么需要双轨筛选？**

| 角色 | Assignee = 本人 | Comment/Watcher/Reporter = 本人 |
|---|---|---|
| 开发人员 | 开发负责人，主要编写代码 | 在他人任务中提供技术支持、关注进展、创建任务 |
| 测试人员 | 负责测试的任务 | 验证他人开发的 Bug、关注待测任务 |
| 产品经理 | 负责的需求 | 跟进其他人实现的功能、监控需求进展 |

**在周报中的区分**：

```
┌─────────────────────────────────────────────────────────────┐
│  本周工作总结（产品/项目角色）                             │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ 负责任务（Assignee = 本人）                          │ │
│  │ - PROJ-123: 用户登录需求（需求评审完成）           │ │
│  │ - PROJ-124: 订单导出功能（开发跟进中）             │ │
│  └─────────────────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ 跟进内容（Comment/Watcher/Reporter）                │ │
│  │ - PROJ-456: 协助开发完成接口对接（Comment）        │ │
│  │ - PROJ-789: 监控需求进展（Watcher）                │ │
│  └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  本周工作总结（技术/开发角色）                             │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ 开发项（Assignee = 本人 + 有关联 Commit）            │ │
│  │ - PROJ-123: 修复用户登录异常                        │ │
│  │   代码：fix(user): 修复空指针问题 (+45/-3)         │ │
│  └─────────────────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ 负责任务（Assignee = 本人，无关联 Commit）           │ │
│  │ - PROJ-124: 技术方案评审（非编码任务）             │ │
│  └─────────────────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ 跟进内容（Comment/Watcher/Reporter）                │ │
│  │ - PROJ-456: 协助张三完成接口对接（Comment）        │ │
│  └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 1.4 姓名识别与匹配

由于不同工具和用户可能使用不同的姓名格式，本 Skill 支持**多种姓名格式的智能匹配**：

| 姓名格式 | 示例 | 匹配方式 |
|---|---|---|
| **中文全名** | 张三、蛋仔 | 精确匹配 |
| **英文名** | San Zhang、Tom | 精确匹配 |
| **拼音（全拼）** | zhangsan、chenziyan | 精确匹配（不区分大小写） |
| **拼音（简写）** | zs、czy,chenzy | 精确匹配（不区分大小写） |

**配置方式**：

在告诉 SOLO 生成周报时，可以提供多个姓名变体：

```
请根据我上传的 issues.csv 生成周报。
姓名：蛋仔
姓名变体：chenziyan, czy, chenzy, Claire
```

SOLO 会自动识别 Comment 中的所有姓名变体，将匹配的 Issue 归类为「跟进内容」。

**匹配优先级**：
1. 精确匹配（中文全名）
2. 忽略大小写的拼音匹配
3. 部分匹配（如 "陈" 可以匹配 "蛋仔"）

### 1.5 核心设计理念

**离线优先**：考虑到企业内网环境的普遍性，本 Skill 采用**离线方式为主**的设计理念：

1. 在本地导出数据（CSV/Excel/JSON）
2. 上传到 SOLO 进行处理
3. 生成并下载报告

**无需网络穿透**，无需开放内网访问权限，数据安全可控。

### 1.6 适用角色与场景

| 角色 | 数据来源 | 报告重点 | 使用方式 |
|---|---|---|---|
| **项目经理/产品经理** | JIRA/TAPD/禅道等 | 任务进度、需求完成情况、Bug修复统计 | 仅上传 issues.csv，声明角色：产品经理 |
| **测试人员** | JIRA/TAPD/禅道等 | 测试用例执行、Bug发现与验证 | 仅上传 issues.csv，声明角色：测试人员 |
| **开发人员** | 项目管理工具 + Git | 任务完成 + 代码实现细节、技术方案 | 上传 issues.csv + commits.json，声明角色：开发人员 |
| **技术负责人** | 项目管理工具 + Git | 整体进度 + 代码质量、技术债务 | 上传 issues.csv + commits.json，声明角色：技术负责人 |

## 二、离线使用方式（推荐）

### 2.1 为什么采用离线方式

| 优势 | 说明 |
|---|---|
| **安全性** | 无需将内网 Git 仓库或 JIRA 暴露给外网 |
| **便捷性** | 只需导出文件，无需配置 VPN 或网络穿透 |
| **灵活性** | 支持任何可导出数据的项目管理工具 |
| **可控性** | 用户决定上传哪些数据，数据范围自主可控 |

### 2.2 通用工作流程

```
步骤1：本地导出数据
    ↓
步骤2：上传到 SOLO workspace
    ↓
步骤3：告诉 SOLO 生成报告
    ↓
步骤4：下载生成的报告
```

### 2.3 各角色详细操作流程

#### 2.3.1 项目/产品人员操作流程

**第一步：从项目管理工具导出数据**

以 JIRA 为例：

1. 登录 JIRA → 进入问题筛选器

2. 设置**双轨筛选条件**（确保不遗漏跟进内容）：

   **方式一：导出 Assignee 是自己的任务（开发项）**
   ```
   assignee = currentUser()
   ```

   **方式二：导出自己参与评论的任务（跟进内容 - Comment）**
   ```
   issueFunction in commented("by chenziyan") 
   ```

   **方式三：导出自己关注的任务（跟进内容 - Watcher）**
   ```
   watcher = currentUser()
   ```

   **方式四：导出自己创建的任务（跟进内容 - Reporter）**
   ```
   reporter = currentUser() AND assignee != currentUser()
   ```

   **方式五：合并导出（推荐）**
   ```
   assignee = currentUser() 
   OR issueFunction in commented("by chenziyan") 
   OR watcher = currentUser()
   OR (reporter = currentUser() AND assignee != currentUser())
   ```

3. 设置时间条件：
   ```
   updated >= -7d（本周）
   或
   updated >= startOfWeek() AND updated <= endOfWeek()
   ```

4. 点击「导出」→ 选择「CSV（所有字段）」

5. 保存为 `issues.csv`

**重要**：确保导出的 CSV 包含以下字段：
- `Issue key`（Issue 编号）
- `Summary`（标题）
- `Issue Type`（类型）
- `Status`（状态）
- `Assignee`（负责人）
- `Reporter`（创建人）
- `Watchers`（关注人）
- `Comment`（评论内容）
- `Updated`（更新时间）

其他工具：
- **TAPD**：需求/缺陷 → 高级筛选 → 导出 Excel（确保包含「评论」字段）
- **禅道**：Bug/任务 → 筛选 → 导出 CSV（确保包含「评论」字段）

**第二步：确认姓名配置**

由于 JIRA 中可能存在多种姓名格式（如中文全名、拼音、英文名），建议在上传前确认：

1. 打开导出的 `issues.csv` 文件
2. 查看 `Comment` 列中其他同事的称呼方式
3. 准备好自己的多个姓名变体

**第三步：上传到 SOLO**

将导出的 `issues.csv` 或 `issues.xlsx` 文件上传到 SOLO 的 workspace folder。

**第四步：告诉 SOLO 生成报告**

```
请根据我上传的 issues.csv 生成周报。
姓名：蛋仔
姓名变体：chenziyan, czy, Claire
模板：企业微信
```

**第五步：审查并调整（如需要）**

SOLO 会自动将 Issue 分为「开发项」和「跟进内容」，如需调整可以：
- 补充缺失的任务描述
- 调整分类归属
- 修改工作内容描述

#### 2.3.2 技术人员操作流程

**第一步：导出项目管理工具数据**

同上，设置**双轨筛选条件**导出 `issues.csv`。

**第二步：本地提取 Git Commit 信息**

下载并运行提取脚本：

```bash
# 下载 extract_commits.py 到本地

# 进入你的 Git 仓库目录
cd /path/to/your/repo

# 运行提取脚本
python3 extract_commits.py --repo . --authors "你的名字"
```

这会生成 `commits.json` 文件，包含：
- Commit 列表及变更统计
- 变更文件路径
- 自动推断的功能模块
- 分支信息

**第三步：上传文件到 SOLO**

- `issues.csv`（项目管理工具导出）
- `commits.json`（Git Commit 提取）

**第四步：告诉 SOLO 生成报告**

**产品/项目人员示例**：
```
请根据我上传的 issues.csv 生成周报。
姓名：蛋仔
角色：产品经理
姓名变体：chenziyan, czy, Claire
模板：企业微信
```

**技术/开发人员示例**：
```
请根据我上传的 issues.csv 和 commits.json 生成周报。
姓名：蛋仔
角色：开发人员
姓名变体：chenziyan, czy, Claire
模板：企业微信
```

**角色声明说明**：
- 声明为「产品经理」「项目经理」「测试人员」→ 报告使用「负责任务」「跟进内容」分类
- 声明为「开发人员」「技术负责人」→ 报告区分「开发项」（有代码提交）和「负责任务」（无代码提交），如有代码提交则在开发项中追加代码实现的描述，无需体现具体代码
- 未声明角色时，根据是否提供 commits.json 自动推断

**第五步：审查并调整（如需要）**

SOLO 会自动根据角色将 Issue 分类，如需调整可以：
- 补充缺失的任务描述
- 调整分类归属
- 修改工作内容描述

## 三、在线使用方式（可选）

### 3.1 适用场景

- Git 仓库可公网访问（GitHub/GitLab 等）
- SOLO 与内网 Git 服务器在同一网络环境
- 快速测试或演示

### 3.2 使用方式

直接告诉 SOLO 仓库地址：

```
请从 Git 仓库 http://gitlab.company.com/project/repo.git
生成本周周报，作者：张三，模板：企业微信
```

**限制**：
- 需要仓库可访问
- 需要认证时需提供凭据
- 无法访问内网私有仓库

## 五、数据分类与筛选逻辑

### 5.1 角色识别与任务分类

本 Skill 根据**用户角色**和**数据特征**智能分类任务：

#### 角色识别逻辑

```
IF 用户声明角色为 "产品经理" OR "项目经理" OR "测试人员"
   OR (未提供 commits.json)
THEN 归类为「产品/项目角色」
     使用「负责任务」而非「开发项」

IF 用户声明角色为 "开发人员" OR "技术负责人"
   OR (提供了 commits.json 且 Commit 与 Issue 有关联)
THEN 归类为「技术/开发角色」
     区分「开发项」和「负责任务」
```

#### 技术角色的细分

对于技术/开发人员，Assignee = 本人的任务进一步细分：

| 子分类 | 识别条件 | 说明 |
|---|---|---|
| **开发项** | Assignee = 本人 AND 有关联的 Commit | 实际编写代码的开发任务 |
| **负责任务** | Assignee = 本人 AND 无关联 Commit | 技术评审、方案设计、非编码任务 |

**示例**：

| Issue | Assignee | 关联Commit | 技术角色分类 | 产品角色分类 |
|---|---|---|---|---|
| `PROJ-123` | 张三 | 有 | 开发项 | 负责任务 |
| `PROJ-124` | 张三 | 无 | 负责任务 | 负责任务 |
| `PROJ-456` | 李四 | - | 跟进内容 | 跟进内容 |

### 5.2 双轨筛选机制

本 Skill 采用**双轨筛选**确保周报内容完整：

| 筛选条件 | 含义 | 报告分类 |
|---|---|---|
| **Assignee = 本人** | 自己是该任务的负责人/开发者 | **开发项** |
| **Comment 包含本人** | 本人在该任务下回复或跟进过 | **跟进内容** |
| **Watcher = 本人** | 本人关注该任务的进展 | **跟进内容** |
| **Reporter = 本人** | 本人创建的任务 | **跟进内容** |

### 5.3 内容区分规则

#### 产品/项目角色 - 负责任务（Assignee = 本人）

**识别规则**：
```
IF Assignee 匹配本人姓名（任意格式）
THEN 该 Issue 归类为「负责任务」
```

**报告展示**：
- 作为主要负责的工作内容展示
- 展示任务进度、状态、关键节点
- 不关联代码信息

**示例标题**：
- 产品经理：「负责任务」「需求管理」「项目推进」
- 测试人员：「测试任务」「用例执行」「Bug验证」
- 项目经理：「负责任务」「项目协调」「进度管理」

#### 技术/开发角色 - 开发项（Assignee = 本人 + 有关联Commit）

**识别规则**：
```
IF Assignee 匹配本人姓名（任意格式）
AND 存在与该Issue关联的Git Commit
THEN 该 Issue 归类为「开发项」
```

**报告展示**：
- 作为主要开发工作展示
- 关联 Git Commit，展示代码实现细节
- 显示代码变更统计（新增/删除行数）

#### 技术/开发角色 - 负责任务（Assignee = 本人 + 无关联Commit）

**识别规则**：
```
IF Assignee 匹配本人姓名（任意格式）
AND 不存在与该Issue关联的Git Commit
THEN 该 Issue 归类为「负责任务」
```

**典型场景**：
- 技术方案评审
- 代码审查（Code Review）
- 技术调研
- 架构设计
- 文档编写

#### 跟进内容（Comment/Watcher/Reporter 包含本人）

**识别规则**：
```
IF (Comment 中包含本人姓名（任意格式）
    OR Watcher 包含本人
    OR Reporter = 本人)
AND Assignee != 本人
THEN 该 Issue 归类为「跟进内容」
```

**跟进类型细分**：

| 类型 | 识别条件 | 典型场景 |
|---|---|---|
| **Comment参与** | Comment 包含本人姓名 | 在他人任务中回复、提供技术支持、验收确认 |
| **Watcher关注** | Watcher 列表包含本人 | 监控任务进展、等待任务完成进行下一步工作 |
| **Reporter创建** | Reporter = 本人 | 创建的任务分配给其他人、需求/缺陷上报 |

**报告展示**：
- 作为协助/跟进内容展示
- 标注跟进类型（Comment/Watcher/Reporter）
- 提取本人评论的关键信息（如为Comment类型）
- 标注原负责人

**完整示例**：

| Issue | Assignee | Reporter | Watcher | Commit | 产品角色 | 技术角色 |
|---|---|---|---|---|---|---|
| `PROJ-123` | 张三 | 李四 | - | 有 | 负责任务 | 开发项 |
| `PROJ-124` | 张三 | 李四 | - | 无 | 负责任务 | 负责任务 |
| `PROJ-456` | 李四 | 王五 | 张三 | - | 跟进内容(Comment) | 跟进内容(Comment) |
| `PROJ-789` | 李四 | 张三 | - | - | 跟进内容(Reporter) | 跟进内容(Reporter) |
| `PROJ-101` | 李四 | 王五 | 张三 | - | 跟进内容(Watcher) | 跟进内容(Watcher) |

### 5.4 姓名识别与匹配

SOLO 支持多种姓名格式的智能匹配：

| 姓名格式 | 示例 | 匹配方式 |
|---|---|---|
| 中文全名 | 张三、蛋仔 | 精确匹配 |
| 英文名 | San Zhang、Claire | 精确匹配 |
| 拼音（全拼） | zhangsan、chenziyan | 不区分大小写匹配 |
| 拼音（简写） | zsy、czy | 不区分大小写匹配 |

**匹配策略**：
1. 提取 Comment 中所有发言人的名字
2. 尝试将名字转换为多种格式
3. 与配置的姓名变体进行匹配
4. 返回匹配结果

## 六、数据融合策略（技术人员专用）

### 6.1 融合逻辑

当同时提供 Issue 列表和 Git Commit 时，SOLO 按以下策略融合：

```
┌─────────────────────────────────────────────────────────────┐
│  融合优先级                                                  │
│  1. Issue 为主 → 描述"做了什么任务"                         │
│  2. Commit 为辅 → 如果Commit从关键字或内容上能匹配到Issue，则利用commit message补充"代码实现"情况，无需体现行数等。如果Commit从关键字或内容上能匹配到Issue，则直接当一个开发项描述，描述功能无需体现行数。                
│  
│  3. 模块归类 → 按功能模块组织展示                           │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 融合示例

| Issue | Commit | 融合后描述 |
|---|---|---|
| `PROJ-123 修复用户登录异常` | `fix(user): 修复登录时的空指针` | **用户模块** - 🐛 Bug修复：修复用户登录异常（空指针问题） |
| `PROJ-124 新增订单导出` | `feat(order): 实现导出接口` | **订单模块** - ✨ 新功能：新增订单导出功能（接口实现） |
|  | `task: 调整调价函模板` | **费用模块** - ⚡ 优化/任务：优化调价函模板（语句优化） |

### 6.3 状态映射

| Issue 状态 | 报告分类 | 说明 |
|---|---|---|
| `Done` / `Closed` / `Resolved` | 完成事项 | 本周已完成的工作 |
| `In Progress` / `进行中` | 进行中 | 尚未完成的工作 |
| `To Do` / `Open` / `新建` | 计划 | 下周待处理的工作 |

### 6.4 类型标签

| Issue 类型 | 标签 | 说明 |
|---|---|---|
| `Bug` / `缺陷` | 🐛 Bug修复 | 问题修复类工作 |
| `Story` / `需求` / `Feature` | ✨ 新功能 | 功能开发类工作 |
| `Task` / `任务` / `Improvement` | ⚡ 优化/任务 | 优化改进类工作 |

## 十、项目管理工具详细集成指南

### 10.1 JIRA 导出步骤

**步骤1：创建筛选器**

1. 登录 JIRA → 点击「问题」→「搜索问题」
2. 设置筛选条件：
   ```
   负责人 = 当前用户()
   且 更新日期 >= -7d（本周）
   ```
3. 点击「保存为」→ 命名筛选器

**步骤2：导出 CSV**

1. 在筛选结果页面点击「导出」
2. 选择「CSV（所有字段）」
3. 保存文件为 `issues.csv`

**步骤3：（可选）自定义字段**

如需导出更多字段：
1. 点击「列」→「自定义列」
2. 添加需要的字段（如：描述、优先级、标签等）
3. 重新导出

### 10.2 TAPD 导出步骤

**步骤1：进入需求/缺陷列表**

1. 登录 TAPD → 进入项目
2. 点击「需求」或「缺陷」

**步骤2：设置筛选条件**

1. 点击「高级筛选」
2. 设置条件：
   - 处理人 = 自己
   - 最后修改时间 = 本周

**步骤3：导出 Excel**

1. 点击「导出」→「导出 Excel」
2. 选择「导出所有字段」
3. 保存文件为 `issues.xlsx`

### 10.3 禅道导出步骤

**步骤1：进入 Bug/任务列表**

1. 登录禅道 → 进入项目
2. 点击「Bug」或「任务」

**步骤2：设置筛选条件**

1. 点击「筛选」
2. 设置条件：
   - 指派给 = 自己
   - 截止日期 = 本周

**步骤3：导出 CSV**

1. 点击「导出」→「导出 CSV」
2. 选择需要的字段
3. 保存文件为 `issues.csv`

### 10.4 数据格式映射表

不同工具的状态和类型字段可能不同，SOLO 会自动识别以下常见值：

| 工具 | 完成状态 | 进行中状态 | 待处理状态 |
|---|---|---|---|
| JIRA | Done, Closed, Resolved | In Progress | To Do, Open, Backlog |
| TAPD | 已解决, 已关闭 | 实现中, 处理中 | 新建, 待处理 |
| 禅道 | 已关闭, 已解决 | 进行中 | 待处理, 新建 |

| 工具 | Bug类型 | 需求类型 | 任务类型 |
|---|---|---|---|
| JIRA | Bug | Story, Feature | Task, Sub-task |
| TAPD | 缺陷, Bug | 需求, Story | 任务, Task |
| 禅道 | Bug, 缺陷 | 需求, Story | 任务, Task |

## 十一、高级功能

### 11.1 多作者别名合并

当同一个开发者在 Git 中使用了不同的用户名（如中英文名），可以合并生成一份周报：

```bash
python3 extract_commits.py --repo . --aliases "张三,San Zhang"
```

```bash
python3 extract_commits.py --repo . --since 2026-05-01 --until 2026-05-15
```

```bash
python3 extract_commits.py --repo . --type monthly --authors "张三"
```

```bash
# 提取数据
```

## 十二、常见问题

### Q1: 为什么采用离线方式为主？

**A**: 企业内网环境通常无法直接从外部访问，离线方式通过文件上传避免了网络穿透的复杂性和安全风险。

### Q2: 导出的 CSV 文件很大怎么办？

**A**: 可以在项目管理工具中设置更精确的筛选条件（如仅导出本周更新的 Issue），或仅导出必要字段。`project = 项目名 AND summary ~ 标题关键字 AND status in ("In Progress", "To Do", "In Review") AND  (issueFunction in commented("by chenziyan") OR  assignee in (currentUser())  AND updated >= 本周开始时间 AND updated <= 本周结束时间 ORDER BY priority DESC, updated DESC`

### Q3: Git Commit 信息不够详细怎么办？

**A**: 使用增强版 `extract_commits.py`，它会自动提取变更文件路径、推断功能模块，并合并关联提交。

### Q4: 如何自定义模板？

**A**: 复制现有模板文件，修改标题和内容格式，上传到 SOLO 时指定自定义模板路径即可。

### Q5: 可以支持其他项目管理工具吗？

**A**: 只要工具支持导出 CSV/Excel 格式，且包含基本的字段（标题、状态、负责人、时间），SOLO 就可以处理。
